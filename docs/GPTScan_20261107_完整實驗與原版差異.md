本文件描述 **2026-11-07 串流修正後的最小適配 baseline**，不是先前 OraclePrice 版本或 11/06 的試跑。依本輪保存的 source snapshot、hashes、workflow 與 Judge artifacts 整理。

## 2. 原版 GPTScan 如何執行？

```text
使用者準備 Solidity repo／framework／compiler／dependencies
    ↓
來源資料夾輸入 -s
    ↓
Falcon 編譯與程式分析模型 ＋ source parser／Java CallGraph
    ↓
載入規則資料夾中的原版規則
    ↓
函式名稱、內容、參數、visibility 等規則特徵篩候選
    ↓
LLM 判斷 scenario／property；需要時加入 caller context
    ↓
LLM 擷取該規則指定的變數或 statements
    ↓
原版 static checker，例如 data dependency、first deposit、order check
    ↓
合併 findings → 原生 output JSON 與 metadata
```

原版不是任意掃描整個 repo 後由 LLM 自由寫完整 audit report，而是規則引導 LLM 問答，再搭配程式分析。

原版 CLI 使用 source、output 與 API key。README 支援部分 Hardhat／Truffle／Brownie 專案，也建議單檔 Solidity 放在資料夾輸入；並非一定要 flatten。使用者要自行準備可編譯環境。

## 3. 本輪從頭到尾怎麼執行？

```text
固定 repo source ref + Reusable Dataset build.json
    ↓
前置準備：Docker setup／framework compile → Crytic Compile archive
    ↓
本輪直接重用固定 archive，驗證來源與分析範圍
    ↓
建立獨立 source snapshot、路徑重定位
    ↓
Falcon 從 archive 載入；不重新編譯
    ↓
GPTScan：七條原版規則＋price instruction
    ↓
同一 gpt-5.6-luna 模型，經本機 gateway 問答
    ↓
原版解析、checker 與逐候選容錯
    ↓
記憶體中的結果直接組成 PredictionCase，寫出 JSON
    ↓
逐 repo schema 驗證；另外記錄執行錯誤
    ↓
固定版本 benchmark_eval ＋ gold ground truth
    ↓
LLM Judge → matching／metrics → report.md
```

本輪有先執行 evaluator 內建 OAuth smoke。完整分析與評估由 `scripts/run_upstream7_experiment.py --run-judge` 串接，沒有挑選各次最好結果，也沒有混用先前已成功的 predictions。

## 4. Dataset 與編譯接入：改了什麼？

### 4.1 Docker、build.json、archive 各自的角色

- **Docker image**：提供已準備的 compiler／framework 工具環境。
- **build.json**：每個 repo 的 build recipe，包括固定來源、project location、toolchain、setup／compile／materialize 與 artifact 設定；不是 dependencies 本身，也不是編譯產物。
- **Crytic Compile archive**：保存編譯上下文，包括 embedded source、AST、bytecode、source maps 與 compiler 資訊等。
- **Falcon**：讀取這些編譯資訊，建立 GPTScan 的程式分析模型。不是與 Crytic Compile 二選一。

前置工作曾使用 Docker 與 Reusable Dataset recipes 建立／整理這些產物；**本輪 23 repo 分析直接重用既有 archives，沒有逐 repo 再做一次 Docker compile**。

編譯準備在 Docker；本輪 GPTScan、Falcon、client 與 orchestration 在本機執行，LLM 推論是遠端服務。不是整套 GPTScan 與 Judge 都在 container 裡。

### 4.2 具體接入差異

| 原版 | 本輪適配 | 原因與限制 |
|---|---|---|
| Falcon 對 source project 執行編譯 | 從固定 archive 載入 Falcon | 重用 dataset 已驗證環境，避免重新猜 framework |
| 來源／依賴由本機環境決定 | 來源 ref、embedded bytes、scope、archive 雜湊等檢查 | 避免分析錯誤版本；不是新增漏洞判斷 |
| 原始來源路徑 | adapter 建 snapshot、重定位並保留 logical-path mapping | 容器／Linux 路徑需在本機可用；來源文字不改 |
| 原版目錄名稱與檔名篩選 | archive 模式由明確 target inventory／scope 決定可分析檔案 | **覆蓋範圍不保證與原版目錄掃描相同**，需披露 |
| Java name-only graph | archive 模式使用 compiler signature、source identity 與 Falcon resolved calls | 處理 overload；**caller context 可能不同，這是實質適配差異** |
| 舊版 Falcon 的 AST／IR 能力 | 限定測試版本的 compatibility 層 | 讓 dataset 可載入；沒有新增經濟攻擊 checker，部分新 EVM 表示仍有限制 |

七份 legacy archive 走明確的 source comparison 路徑，不偽稱具有新版完整 build provenance；其餘十六份使用 strict 模式。必要時保留完整 framework compiler context，再依 production roots 與 import closure 選擇範圍，不把編譯依賴提早刪除。

主要檔案：`scripts/run_reusable.py`、`src/reusable_archive.py`、`src/archive_scope.py`、`src/antlr4helper/callgraph.py`、`src/falcon_compat.py`、`src/static_check.py`、`src/falcon_adapter.py`。

原版可在 compile 失敗後繼續部分分析；本次 archive 接入／preflight 無法成立時不拿不明或缺失上下文繼續。這是明確的輸入有效性條件，不可宣稱原版與本輪所有 failure policy 完全一樣。

## 6. 模型連接與串流修正

| 項目 | 原版 | 本輪 |
|---|---|---|
| 連接 | OpenAI API key、ChatCompletion | 本機 loopback gateway、授權的 Codex 模型 |
| 模型 | 原程式指定 GPT-3.5／GPT-4 路徑 | 統一 gpt-5.6-luna；不因 GPT4 flag 自動切模型 |
| 回覆協定 | ChatCompletion message content | Responses 相容 SSE → 完整 output text |
| 原版模型參數 | 原請求設定 temperature 0、top_p 1 | gateway detector payload 沒有同樣明確指定這兩個參數，不能宣稱 sampling 設定完全一致 |
| 暫時網路／HTTP問題 | 部分持續重試，受外層問答限時控制 | 保留相應傳輸重試；不作語意格式重問 |
| 新增的串流恢復 | 無此 gateway 模式 | 正確處理 SSE framing；明確可恢復故障最多額外重試一次相同請求 |

串流修正位於 `src/model_transport.py`，處理多行data、CRLF／BOM、heartbeat、缺少completed、connection reset與明確server error。重試時model、instruction、question與payload不改，不取最好一次回答、不使用partial text當成功。

內容／長度限制、登入／權限錯誤或未知原因的incomplete不盲目重試、不提高限制。回覆本身若是完整文字但不符合GPTScan所需JSON，交由原版解析，不由連接層修好或重問。

登入資料只在本機執行時讀取，不放入snapshots、predictions或文件。本次未修改共享OMP服務或改用API key；Judge使用我們專案原本的OAuth client，與detector gateway不是同一個client。

**本輪紀錄沒有找到串流失敗、傳輸重試或問答timeout。** 這是本次觀察，不保證未來永遠不會出現。

## 7. 分析與錯誤處理：哪些保留、哪些撤回？

### 保留原版分析行為

- 候選篩選、scenario／property問答、caller情境、變數／statement擷取及checker的主流程。
- 原版 yes/no startswith 判定、numbered choices及static JSON解析方式。
- 原版rule index行為；早期順手加入的索引修正已撤回。
- FirstDeposit checker原本的字串／括號解析與logger.error，未改成更強的IR checker。
- 局部例外的catch／繼續策略，包含某些static check外層例外被設為False。

### 本輪已不存在的額外保護

- 不再因一次failed event全域封鎖後續模型請求。
- 不再因任意ERROR log禁止合法PredictionCase輸出。
- 沒有新增CandidateRejected例外分類來改寫原版錯誤路徑。
- 沒有對模型的語意回答施加額外schema重答或格式修補。

### 只新增執行診斷，不用它改分數

| 狀態 | 意義 |
|---|---|
| completed | 程序跑到結束、有有效輸出，未記錄分析錯誤 |
| completed_with_errors | 按原版容錯跑到結束、有有效輸出，但部分處理曾報錯 |
| failed／timed_out／schema_failed | 未正常結束、總時限到或輸出格式無效 |

completed_with_errors不是原版名稱，也不是新的漏洞判定。錯誤事件數不等於失敗候選數；同一問題可以記錄多條ERROR。

**沒有回報的候選不能視為已證明安全**。Judge只評估最後實際輸出的findings，不能補回工具因例外漏掉的候選。

## 8. 直接輸出 Judge input：如何改？

### 舊版與本輪差別

原版最後將內部結果轉成原生 `results` JSON 寫檔。本輪仍在記憶體整理該結果，但改由 `src/prediction_export.py` 直接寫成 `PredictionCase`。

```text
內部 findings／locations
    ↓ deterministic mapping
-o prediction_case.json
```

不需要先寫原生output.json再外部轉檔；也不是要求LLM直接生成整份PredictionCase。`--native-output`是選用debug，`--prediction-output`僅保留舊CLI相容alias；本輪runner使用主要 `-o`。

| PredictionCase欄位 | 來源 |
|---|---|
| repo_id | runner指定的固定repo identity |
| detector_metadata | detector版本與指定模型 |
| finding_id | repo、rule code與locations的穩定雜湊，不使用ground-truth ID |
| title／description | 原版rule output模板 |
| impact | 本次開發時逐條補入rule的模板，非逐finding LLM生成 |
| mitigation | 原版recommendation原樣映射，不重新撰寫 |
| vulnerable_code | 檔案、contract、signature與source range的程式定位 |
| severity／rule_id／report_basis | 原生或轉換provenance資訊 |

vulnerable_code通常指向整個候選函式區間，必要時包含caller等多處位置；不是LLM找出的逐行漏洞證明，也不是ground truth提供的位置。

字串非空不代表impact／mitigation具體正確，Judge仍會評分。沒有人工補寫、LLM enrichment或讀ground truth來生成finding。

輸出採atomic JSON write與路徑／必要欄位檢查，再使用正式benchmark_eval contract驗證。合法零findings可輸出空predictions；真正無效輸出不捏造一份空input替代。

## 9. LLM Judge 與 Evaluation 怎麼接？

本輪由GPTScan repo的wrapper串接，但評分邏輯是我們專案的固定evaluator快照，不是GPTScan自帶、也不是另外重寫。

```text
實驗資料夾/gptscan/predictions/<repo_id>.json
    ↓
實驗資料夾/evaluator_source/ 下執行 python -m src.benchmark_eval
    ＋快照中的正式ground truth
    ↓
llm_judge/manifest.json
llm_judge/judge_artifact.json
llm_judge/report.json
llm_judge/report.md
```

Predictions沒有搬回主要prototype checkout；從外部實驗目錄指定路徑即可。使用 `prototype-scar/.venv/bin/python` 提供runtime，但實際載入的evaluator source是快照。

本輪matching為greedy、threshold 0.5、weight profile end-to-end-v2、judge prompt benchmark-judge-v3。R／L／I／M評分、matching、metrics與report由固定評估器負責。沒有為GPTScan調整rubric／threshold／ground truth，也沒有因completed_with_errors改寫verdict或補分。

## 11. 公平比較必須披露的限制

1. 模型不同於原版程式，detector sampling參數也不宣稱完全相同；不能直接當成原論文成績。
2. 明確選七條規則與price instruction，是task-focused baseline，不是原版general全規則設定。
3. Scope與compiled CallGraph可能影響覆蓋及caller context；archive／IR compatibility不是純JSON格式改動。
4. 原版checker或解析例外仍可能漏報，保留而非為提高成績修正。
5. impact是新增規則模板，recommendation完全保留；Judge可能因其泛用性降低I／M分數，不能事後人工補強。
6. 傳輸重試只針對明確協定／暫時故障，不做語意重問、不挑最高分run。這輪沒有觀察到重試，不代表原版與適配版連接層完全一致。
7. 先前試跑曾用同組資料除錯；本輪並非獨立holdout評估，不宣稱無任何開發期資料接觸。
